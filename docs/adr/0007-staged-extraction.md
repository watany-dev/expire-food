# ADR 0007: Gemma 4 を基本にした段階的な読み取り

- 状態: 採用（判定モデルは ADR 0013 で高補正モードのときだけ使うことにした）
- 日付: 2026-09-25
- ADR 0003 のモデル選定とプロンプトの形を置き換える（`/api/extract` の受け口・レート制限・クライアント JS の配信方法は ADR 0003 のまま）

## 背景

ADR 0003 では 1 回のモデル呼び出しで商品名・期限・種別・確信度を返させていた。実際のパッケージには、ブランド名と商品名、製造日と賞味期限、キャンペーンの締切など候補が複数あることが多い。モデルの自己申告の `confidence` では、どれを選んだかも、なぜ読めなかったかも分からない。読めなかったときにできるのは、写真全体を送り直すか手入力することだけだった。

## 決定

写真 → 読み取りモデルで抽出 → コードで検証 → 意味的に曖昧なときだけ判定モデル → 確定 / 部分再読 / 再撮影、の段階で処理する。順序は `src/domain/pipeline.ts` の `extractItem` 1 か所にまとめ、本番（`src/routes/extract.ts`）とモデル比較（`scripts/extract-eval.ts`）で共有する。

1. **抽出（読み取りモデル）**: `@cf/google/gemma-4-26b-a4b-it`。正規化した答えではなく、読めた原文を返させる
   - `names`: 印字された商品名の候補（目立つ順）
   - `dates`: 印字された日付ごとに `text`（原文）と `label`（近くの文言。「賞味期限」「製造日」など）
   - `issue`: 日付があるのに読めない理由（`blur` / `cut_off` / `glare` / `too_small`）
   - 読めない項目は空の配列、または `label: null` で表す。`response_format` の `json_schema` で形を固定し、`enable_thinking: false` で考えさせない（写すだけなので、応答時間と Neurons を抑える）
2. **検証（コード。`resolveReading`）**
   - 日付として成立するか（`normalizeDate`。ADR 0003 のまま）
   - 製造日などの期限でない表示（ラベルが「製造」「加工」「包装」「採卵」）を外す。期限の文言が付いた日付があれば、付いていない日付より優先する。同じ日付はまとめる
   - 商品名は表記揺れ（NFKC・空白・大文字小文字）をまとめる。候補が複数なら、そのスペースに登録済みの商品名（`listItemNames`）を商品マスタ代わりにして、ちょうど 1 つ一致すればそれで確定する。D1 はこのときだけ読む
3. **判定（`typesafe/jev`。`src/domain/judge.ts`）**: コードで決めきれず、候補が複数残った項目だけを Choice の質問にする。`state` は抽出結果、選択肢は候補の原文そのもの。確信度 0.7 未満の答えと候補に無い答えは採らない
   - Jev が失敗しても 502 にせず、候補を返してユーザーに選ばせる（`judge failed` をログに出す）
4. **決定（`decide`）**: 応答の `next` で次の行動を返す
   - `confirm`: 期限が決まった、または期限の候補が複数ある（読めてはいるので、候補から選ばせる）
   - `retake`: 期限の候補が無く、`issue` が `blur` / `cut_off` / `glare`。または部分再読でも読めなかった
   - `reread`: それ以外（期限の候補が無い・小さすぎる）。期限の部分だけを切り出して `part=date` で再読する
   - `confidence` はモデルの自己申告ではなく、コードだけで決まった期限は `high`、判定モデルが選んだ期限は `medium`、決まらなければ `low`

### 部分再読と再撮影

- 再処理では商品全体を送り直さず、期限の部分だけを切り出して送る。切り出しは縮小前の写真から行い、小さな印字を潰さない
- 切り出す領域は、まずユーザーの指定（写真を表示したキャンバスを指でなぞって囲む）から得る。撮影ガイド（枠を出して撮らせる）と端末の OCR（`TextDetector` などの座標）は、同じ `part=date` に切り出した画像を送る別の入口として後から足せる
- 部分再読は 1 回まで。それでも読めなければ、モデルを変えて読み直すのではなく再撮影に進める（ピンぼけや印字欠けはモデルを変えても直らない）

### Jev の呼び出し形式

Workers AI の `typesafe/jev` は `wrangler types` が生成する `AiModels` にまだ無いので、`src/platform/ai.ts` で `run` の型を外して呼ぶ。入力は `{ state, questions: { name?: { type: "choice", instructions, criteria } } }` の形で送る。応答の外側（`answers` の有無、`result` での包み）は `parseJudgement` がどれでも読めるようにし、読めなければ何も選ばない。公開資料から確かめられたのはこの形までで、実物での確認は ROADMAP Phase 3 の残タスクで `bun run extract-eval` を使って行う。

## 影響

- 最初の読み取りモデルの呼び出しは毎回必ず発生する。期限の候補が複数あれば Jev の答えに関係なく `confirm` になるので、Jev で再読は減らない（ADR 0013）
- 1 回の読み取りで AI を最大 2 回（Gemma + Jev）、部分再読を入れると最大 4 回呼ぶ。レート制限は `/api/extract` のリクエスト単位のまま（部分再読も 1 回と数える）
- `/api/extract` の応答に `next` / `name_candidates` / `date_candidates` が増える。フォームは商品名の候補を `<datalist>` に、期限の候補を案内文に出す
- 商品マスタは持たず、スペースの登録履歴で代える。登録が増えるほど商品名の候補を判定モデルなしで決められる
